# Upgrading to 0.1.0-preview.10

From 0.1.0-preview.9 · in progress.

**Campaign revisions R2 and R3: ONE migration for both, with a one-line data step, three
removed public members (one of them breaks binaries only), and one default that changed — the
retry ladder.** Everything else in R2 and R3 is opt-in. If you do not compose
`Goldpath.Campaign`, none of that touches you.

**Every app that maps an admin surface: a read role (admin contract R4.1).** No code change is
needed, and no operator loses access. What changes is who may read, and what a refused verb
says. See the last section.

## Campaign revisions R2 and R3 — one migration, one data step

R2 was never published on its own, so an adopter coming from preview.9 generates one migration
for both revisions (campaign RFC R3, "The one migration", owner decision Q1).

R2 adds two columns to `GoldpathCampaigns` (`Priority`, `EnumeratedKey`), five nullable
columns to `GoldpathCampaignItems` (`NextAttemptAt`, `AckDeadline`, `CorrelationId`,
`ErrorCode`, `ReleasedAt`), one small table (`GoldpathCampaignParkedCallbacks` — callbacks
that arrived before the acceptance they answer), and replaces the items' `(CampaignId, State)`
index with three: `(CampaignId, State, NextAttemptAt)`, `(CampaignId, CorrelationId)` and
`(CampaignId, State, ReleasedAt)`.

R3 adds eleven columns to `GoldpathCampaigns` and one small table, and **nothing to
`GoldpathCampaignItems`** — no column and no index:

| Column on `GoldpathCampaigns` | Type | Value on every existing row |
|---|---|---|
| `StartAt` | `DateTimeOffset?` | null — starts as soon as its snapshot is ready, as today |
| `MaxAwaitingAck` | `int?` | null — R2's single in-flight ceiling |
| `AwaitingAckCount` | `long` | 0 |
| `PolicyVersion` | `long` | 0 |
| `SuspendOnFailureRatio` | `double?` | null — never suspends |
| `SuspendWindow`, `SuspendMinSample` | `int?` | null — the module defaults |
| `WindowOutcomes`, `WindowFailures` | `long` | 0 |
| `WindowStartedAt` | `DateTimeOffset?` | null |
| `SuspendedReason` | `string?` (512) | null |

The table is `GoldpathCampaignCeilings` (primary key `Kind`, `Name`): the live global and
target-system release ceilings, seeded from code by the leader. Every default above is R2's
behaviour, so **R3 adds no data step**, and its columns are a metadata change on PostgreSQL 11+
and SQL Server that can be applied while campaigns run. After updating the packages:

```bash
goldpath db add CampaignR2R3
```

Then add ONE line at the end of the generated migration's `Up` — the data step a package
cannot put into an app-owned migration itself:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // … what EF generated …
    migrationBuilder.GoldpathCampaignR2Backfill();   // pass schema: "…" if your model sets a default schema
}
```

```bash
goldpath check
```

**Why the data step.** R1 wrote a retry waiting on its rung (`AwaitingRetry`) without a ripe
instant; R2 reads only `NextAttemptAt`. The step stamps every such row with the R1 rung it
was waiting on (30 seconds after its first failure, 2 minutes after a later one, from
`CompletedAt`) — PostgreSQL and SQL Server; it touches only those rows and is safe to run
twice. If the line is missed, the engine treats those rows as ripe at once (the remaining
seconds of their rung are waived) — they are never stranded, but the step is the plan.

### The three `CREATE INDEX` statements block writes on a large items table

The new columns are nullable, so adding them is a metadata change on PostgreSQL 11+ and SQL
Server. The three indexes are not: a plain `CREATE INDEX` blocks writes to
`GoldpathCampaignItems` for as long as it takes to build — minutes at tens of millions of
rows, during which consumers cannot claim and the sink cannot flush. **Apply the migration
between campaigns** (nothing `Running`, consumers idle). If you cannot, replace the three
`migrationBuilder.CreateIndex(…)` calls on `GoldpathCampaignItems` in the generated migration:

PostgreSQL — build each index concurrently, outside the migration's transaction:

```csharp
migrationBuilder.Sql(
    """CREATE INDEX CONCURRENTLY IF NOT EXISTS "IX_GoldpathCampaignItems_CampaignId_State_NextAttemptAt" ON "GoldpathCampaignItems" ("CampaignId", "State", "NextAttemptAt");""",
    suppressTransaction: true);
migrationBuilder.Sql(
    """CREATE INDEX CONCURRENTLY IF NOT EXISTS "IX_GoldpathCampaignItems_CampaignId_CorrelationId" ON "GoldpathCampaignItems" ("CampaignId", "CorrelationId");""",
    suppressTransaction: true);
migrationBuilder.Sql(
    """CREATE INDEX CONCURRENTLY IF NOT EXISTS "IX_GoldpathCampaignItems_CampaignId_State_ReleasedAt" ON "GoldpathCampaignItems" ("CampaignId", "State", "ReleasedAt");""",
    suppressTransaction: true);
```

A concurrent build that fails leaves an `INVALID` index behind: drop it and run the bundle
again. The old index's `DropIndex` can stay as generated (it is quick).

SQL Server — build online (Enterprise or Developer edition, Azure SQL; on Standard edition,
apply between campaigns instead):

```csharp
migrationBuilder.Sql("CREATE INDEX [IX_GoldpathCampaignItems_CampaignId_State_NextAttemptAt] ON [GoldpathCampaignItems] ([CampaignId], [State], [NextAttemptAt]) WITH (ONLINE = ON);");
migrationBuilder.Sql("CREATE INDEX [IX_GoldpathCampaignItems_CampaignId_CorrelationId] ON [GoldpathCampaignItems] ([CampaignId], [CorrelationId]) WITH (ONLINE = ON);");
migrationBuilder.Sql("CREATE INDEX [IX_GoldpathCampaignItems_CampaignId_State_ReleasedAt] ON [GoldpathCampaignItems] ([CampaignId], [State], [ReleasedAt]) WITH (ONLINE = ON);");
```

Keep the index names exactly as above: they are the names EF generated, so the model
snapshot and the database still agree and `goldpath check` stays green.

## Three removed public members — recompile, and one positional edit

All three shipped in preview.8 and are still in preview.9; `PublicAPI.Unshipped.txt` carries
each as `*REMOVED*`. Most adopters call none of them — they are for code that drives the
engine or builds the admin records directly (tests, mostly):

1. `GoldpathCampaignEngine<TContext>.ExecuteItemAsync(…, string? tenant, bool replay, CancellationToken)`
   gains an `int attempt` argument (before `replay`) and returns
   `Task<GoldpathCampaignActionResult>`. **Source- and binary-breaking.**
2. The positional `GoldpathCampaignInfo(…)` constructor gains `Priority` between
   `MaxAttempts` and `WindowOpenNow`. **Source-breaking** for positional construction and
   deconstruction (add the argument), and binary-breaking.
3. The `GoldpathCampaignThrottle(…)` constructor gains an optional `Priority` at the end.
   Source-compatible, but **binary-breaking**: an assembly compiled against preview.9 that
   calls `new GoldpathCampaignThrottle(…)` throws `MissingMethodException` until it is
   recompiled. Recompile; no edit.

One enum value is new (`GoldpathCampaignItemState.AwaitingAck = 7`) — an exhaustive switch
over item states gains a case — and one enum is new (`GoldpathCampaignPriority`). R3 appends
two campaign states, `GoldpathCampaignState.Ready = 8` and `Suspended = 9` (no stored value
moves; an exhaustive switch over campaign states gains two cases), and adds the
`GoldpathCampaignCeiling` entity with its `GoldpathCampaignCeilingKind` enum.

## A default changed: the retry ladder

R1 waited 30 seconds before the second attempt and 2 minutes before every later one, exactly.
R2's default ladder is **30 s, 2 min, 10 min** (the last rung repeats) with **±20% jitter on
every rung**. With `MaxAttempts` of 4 or more, the wait before attempt 4 and later is 10
minutes instead of 2, and no rung is exact any more. To keep R1's ladder:

```csharp
builder.AddGoldpathCampaign<WebApplicationBuilder, AppDb>(campaign =>
{
    campaign.RetryBackoff = [TimeSpan.FromSeconds(30), TimeSpan.FromMinutes(2)];
    campaign.RetryJitter = 0;
    // … your AddCampaign calls …
});
```

Behaviour you will notice without opting into anything, each of it a repair:

- **Pause means now.** A message that reaches a consumer after a pause or an abort claims
  nothing; a release nobody claimed within `OrphanReleaseAfter` (5 minutes) is published
  again, and resume publishes every unclaimed release on the next tick.
- **Abort stamps waiting retries.** A retry waiting on its rung is unsent work: abort now
  stamps it `Aborted` with `Pending` and `Released` (R1 left it waiting forever).
- **What is in flight drains whatever the campaign's state.** The stale-claim sweep now
  reaches paused, closed-window, aborted, expired and finished campaigns too; an interrupted
  claim there lands in the repair queue instead of sitting in `Processing`.
- **A ripe retry claims even when its message outruns the mark** (the real-broker race R2
  found in R1's ladder).

Everything else defaults to R1: `Priority` is Normal, no type has a ceiling, and your
`IGoldpathCampaignItemHandler<T>` keeps its contract (return = success, throw = retryable).

## To adopt the new surfaces (all opt-in)

```csharp
// A target system that answers later: typed results instead of return/throw.
builder.Services.AddScoped<IGoldpathCampaignActionHandler<DeviceTarget>, ConfigPushHandler>();

campaign.AddCampaign<DeviceTarget>("config-push", c => c
    .MaxTargets(50_000_000)
    .MaxTps(200)                                     // the target system's ceiling, shared by every config-push campaign
    .SignedCallbacks(builder.Configuration["Campaign:ConfigPush:CallbackSecret"]!)   // >= 32 bytes, never in source
    .TargetsAfter((services, parameters, afterKey) => /* ids strictly greater than afterKey, ascending */,
        target => target.Id.ToString(CultureInfo.InvariantCulture)));

app.MapGoldpathCampaignCallbacks<AppDb>();          // POST /goldpath/campaign/callbacks/{type}/{campaignId}/{correlationId}
```

- **Callbacks are signed, never anonymous and never an ops credential.** The handler gives
  the target system the callback path — `/goldpath/campaign/callbacks/{context.Type}/{context.CampaignId:N}/{correlationId}`
  — and the target system signs each callback with the type's secret: HMAC-SHA256 over
  `{unix seconds}\n{METHOD}\n{path}\n{raw body}`, sent as `X-Goldpath-Signature: v1=<hex>`
  with the timestamp in `X-Goldpath-Timestamp` (`GoldpathCampaignCallbackSignature.Sign`
  computes it in .NET). A missing, stale (outside `CallbackTimestampTolerance`, 5 minutes)
  or wrong signature is `401`. Mapping the surface without any type that declares
  `SignedCallbacks` refuses to start, and **GP1704** (Error) says so at build time. To rotate
  a secret, deploy `SignedCallbacks(next, previousSecret: current)`, move the target system
  to `next`, then drop `previousSecret` (runbook §10). An authorization policy on top of the
  signature is opt-in: `MapGoldpathCampaignCallbacks<AppDb>(policy: "…")`.
- **Correlation ids name one attempt.** Derive them from the target system's own request id
  or from `context.IdempotencyKey`; a callback that arrives before its acceptance is visible
  is parked (`202`) and settles the moment the acceptance lands.
- **Size `MaxInFlight` for acceptances.** An accepted item holds an in-flight slot until its
  callback or its ack deadline; a campaign at 50 TPS with a 6-hour ack timeout can have far
  more than the default 1,000 acceptances outstanding, and stalls at `MaxInFlight` until
  callbacks drain it.
- **Switching a running type from `Targets` to `TargetsAfter` is safe** if the keyset
  selector keeps the same order: a takeover of a row enumerated by count derives its resume
  key from the target materialized last, and refuses with teaching text when it cannot.

## Admin surfaces: a read role, `goldpath-ops-read` (admin contract R4.1, #297)

**What changes.** Every admin surface (jobs, bulk, notification, archival, file exchange,
approvals, campaign) and the served console now apply the HTTP method rule:
- **Reads:** every `GET` demands the new read policy, `GoldpathPolicies.OpsRead`. Both
  `goldpath-ops-read` (`Goldpath:Auth:OpsReadRole`) and `goldpath-ops` satisfy it.
- **Verbs:** every other method also demands `goldpath-ops`.

**Nothing to do for operators.** An identity provider that grants only `goldpath-ops` sees no
change.

**Two behaviours you will notice:**
- **A refused verb now has a body.** It is a `403` with the admin envelope
  `{ "ok": false, "message": "this verb needs the goldpath-ops role; this identity can read this surface but not act on it" }`,
  where it used to be an empty `403`. The message names the role as you configured it
  (`Goldpath:Auth:OpsRole`).
- **A `GET` answers a `goldpath-ops-read` identity.** It used to refuse that identity with `403`.

**What granting `goldpath-ops-read` discloses.** Granting the role grants **archive retrieval**:
`GET /goldpath/admin/archival/entries/{definition}/{key}` returns the archived document in full,
unmasked, within the holder's tenant scope. That can include personal data under legal hold or
awaiting erasure. Where your archive holds sensitive content, withhold the role, or grant it only
where that read is intended. A metadata-only viewer is not built (open-threads T50).

**Apps that register their own policies without `Goldpath.Auth`.** Such an app may not define
`goldpath-ops-read`. It then keeps the old floor exactly (`goldpath-ops` on every route), and
each surface logs one information line on `Goldpath.AdminSurface` naming the policy to
register.
