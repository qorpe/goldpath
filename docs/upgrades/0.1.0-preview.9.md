# Upgrading to 0.1.0-preview.9

From 0.1.0-preview.8 · in progress.

**One type moved between packages — source-compatible, recompile-only — and the
clean-architecture layout builds with the features it previously could not.**

## `IAuditLogged` moved to `Goldpath.Abstractions`

It was in `Goldpath.AuditTrail`. It is now in `Goldpath.Abstractions`, beside the five
markers it belongs with: `IAuditedEntity`, `ISoftDeletable`, `IMultiTenant`,
`IIntegrationEvent` and `GoldpathPersonalData`.

**What you have to do: recompile. Nothing else.** Both packages declare the type in
`namespace Goldpath`, so no `using` changes and no source edits. If you reference
`Goldpath.AuditTrail` you already reference `Goldpath.Abstractions` transitively, so nothing
new to add either.

**If you ship a binary compiled against preview.8's `Goldpath.AuditTrail`** and load it
beside preview.9 without rebuilding, it will fail to resolve the type. A `TypeForwardedTo`
was tried and withdrawn: `PublicApiAnalyzers` cannot reconcile a forwarded type, reporting
RS0016 (*not part of the declared public API*) and RS0017 (*declared but could not be found*)
for the same symbol in the same build. On a pre-1.0 preview train the recompile is the
cheaper honesty than an analyzer suppression that outlives the reason for it.

### Why it moved

The `clean-architecture` layout puts the entity partial in the `Domain` project. Reaching
`IAuditLogged` there meant referencing `Goldpath.AuditTrail`, which pulls **ASP.NET Core,
EF Core and `Goldpath.Data`** — inverting the dependency direction that layout exists to
teach. A generated app in that layout did not build, and the honest fix was not to reference
the heavy package from `Domain` but to put the bare marker where its siblings already were.

## A generated app with `fileexchange` builds on its first try

On preview.8 it did not. The templates and `goldpath add feature fileexchange` compose
FileExchange with an empty rail block — deliberately, because goldpath never guesses a
counterparty format — and GP2102 warns about exactly that state. The generated apps treat
warnings as errors, so the warning became a build break: **every app generated with
`fileexchange` on preview.8 failed its first build**, from the published packages as much as
from source.

preview.9's templates keep GP2102 a warning in the generated app's `Directory.Build.props`:

```xml
<WarningsNotAsErrors>$(WarningsNotAsErrors);GP2102</WarningsNotAsErrors>
```

The warning still shows on every build until you declare your first `AddRail` — that is what
it is for — but it no longer stops the build. The line is inert in an app without FileExchange.

**If you generated with `fileexchange` on preview.8, or added it with
`goldpath add feature fileexchange`:** add that line to the `<PropertyGroup>` in your root
`Directory.Build.props`, beside `TreatWarningsAsErrors`. Or declare a rail, which removes the
warning outright.

## The clean-architecture layout builds with `idempotency`

Second, unrelated break in the same layout, same shape of cause. `CreateOrder.cs` carries
`[Mediant.Behaviors.Attributes.Idempotent]` and lands in the `Application` project, but **no
template csproj referenced `Mediant.Behaviors`** — in `vertical-slice` the file lands in the
`Api` project and picks it up transitively through `Goldpath.Idempotency`. The template's
`Application` csproj now carries the reference under `UseIdempotency`, with its
`PackageVersion` (central package management makes it two lines, not one).

**Adopters on `vertical-slice`: nothing to do.** Adopters who generated `clean-architecture`
with `idempotency` and added the reference by hand can delete it — regenerating is not
required, and a duplicate reference is harmless either way.

## `goldpath add feature` no longer references `Goldpath.Jobs` twice

Six features ride the jobs runtime — archival, approvals, bulk, campaign, fileexchange,
notification — and each recipe asks for `Goldpath.Jobs`. On preview.8, adding a SECOND one to
an app that already had the first referenced the package again, and NuGet refuses a duplicate
`PackageReference` (NU1504; the generated apps treat warnings as errors, so the app stopped
restoring). The recipe writer now checks each package against the whole project file before
adding it.

**If you hit NU1504 on preview.8:** delete the extra `<PackageReference Include="Goldpath.Jobs" />`
lines from your Api project, keeping one. Nothing else to do.

## `goldpath add feature idempotency` leaves an app that builds

On preview.8 it did not, whenever the app still had the template's sample `CreateOrderCommand`.
GP1001 fails the build while idempotency is composed and a Mediant command is unmarked — on
purpose, since an unmarked command runs twice on a client retry. The template marks its own
sample when generated with `--features idempotency`; the recipe did not, so the first
`dotnet build` after the verb failed.

The recipe now marks the sample with the same four lines the template emits, and in
`clean-architecture` adds `Mediant.Behaviors` to the `Application` project with its
`PackageVersion`, as the template does. Your own commands stay your decision — the verb's
closing note now says outright that GP1001 fails the build until each is marked.

**If you ran the verb on preview.8 and hit GP1001 on `CreateOrderCommand`:** put
`[Mediant.Behaviors.Attributes.Idempotent(KeyProperty = nameof(CreateOrderCommand.Reference))]`
above it, or delete the sample if you no longer use it.

## How both were missed

The nightly golden-manifest matrix had two clean-architecture shapes and neither could reach
these. `GmFourClean` takes no features at all. `GmOneClean` keeps the default broker, which
supplies `Mediant.Behaviors` to `Application` by accident through `Goldpath.Messaging`.
`GmCleanFeatures` is the new shape: clean-architecture, broker-less, carrying the features
whose code the layout MOVES. Both defects were found by `qorpe/coexist` on 2026-09-09,
generating exactly that shape as the first adopter to want it.
